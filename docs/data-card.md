## What we use and what we exclude

| Source file | Used? | Why |
|---|---|---|
| `file.csv` (193 MB) | ✅ metadata only | File copies to USB. The `content` column (file header and topic keywords) is **never read**, to keep to file metadata only |
| `device.csv` (29 MB) | ✅ | USB connect and disconnect, the main evidence in insider scenarios 1 and 2 |
| `logon.csv` (59 MB) | ✅ | Logon times (after-hours) and logons to another user's PC |
| `LDAP/*.csv` (18 monthly snapshots) | ✅ partially | Department, role and departure month. **Names, emails and supervisors are dropped** |
| `answers/insiders.csv` | ✅ | Ground-truth labels for release 4.2 only |
| `http.csv` (14.5 GB) | ❌ | Web browsing is outside file-access scope. The readme also warns that some generated URLs may point to malicious sites |
| `email.csv` (1.4 GB) | ❌ | Outside scope (the brief rules out email monitoring) |
| `psychometric.csv` | ❌ | Big-5 personality scores. Using personality to flag people is the profiling our privacy stance rejects |

## Schema mapping

Every source maps to one shared event schema (`src/ueba/schema.py`):

| Schema field | `file` events | `device` events | `logon` events |
|---|---|---|---|
| `event_type` | `file` | `device` | `logon` |
| `user_id` | Pseudonym `U0001`–`U1000`, assigned in sorted order of CERT ID | same | same |
| `department` | LDAP `functional_unit` from the user's latest snapshot, prefix stripped (`5 - SalesAndMarketing` → `SalesAndMarketing`). CERT's typo "Adminstration" is corrected | same | same |
| `role` | LDAP `role` from the latest snapshot | same | same |
| `timestamp` | `date` | `date` | `date` |
| `action` | always `copy_to_usb` | `usb_connect` / `usb_disconnect` | `logon` / `logoff` |
| `device_id` | `pc` | `pc` | `pc` |
| `file_id` | filename | — | — |
| `file_type` | From extension: doc/pdf → document, txt → text, jpg → image, zip → archive, exe → executable | — | — |
| `file_category`, `file_department`, `sensitivity` | **`unknown`** | — | — |
| `bytes` | null, not recorded | — | — |

The users table adds four derived fields:

- `assigned_pc`: the PC the user logs on to most often;
- `first_seen_month` and `last_seen_month`: from the directory snapshots;
- `left_organisation`: the user is missing from the final snapshot.

## Assumptions (all reviewable)

1. **Sensitivity, category and owning department are `unknown`, not guessed.** CERT filenames are random 8-character strings with no folder path, such as `EYPC9Y08.doc`. The only signal for these fields is the file-contents keywords, which we deliberately don't read. Deriving sensitivity from extension (say ".zip = confidential") would be invented and indefensible.
2. **Department means functional unit.** It has 6 values, comparable with the synthetic data. The finer CERT department (22 values) is kept as `sub_department`.
3. **Assigned PC is the most frequent logon PC.** CERT says each user has one assigned PC but doesn't list it.
4. **A user's department and role come from their latest directory snapshot.** Role changes during the period, such as Salesman → SalesManager, are not tracked over time.
5. **Two users have no functional unit** (a President and an Administrative Assistant). Their department is `unknown`, which covers 1,652 events.

## Known limitations

- **"Dense needles."** The readme says r4.2 has an unrealistically high share of insider activity: 70 of 1,000 users. Real-world precision will be lower than CERT precision.
- **Departure leaks the label.** All 70 insiders left the organisation, compared with 155 of 1,000 users overall. Using `left_organisation` as a detection feature would inflate results. It's excluded from detectors and may be reported only as a separate ablation.
- **File actions are only USB copies.** The brief's views, downloads and cross-department or sensitive access can't be evaluated on CERT. They are covered by the synthetic testbed instead.
- **Some scenario evidence is in sources we exclude.** Scenario 1 uploads go through `http.csv`, scenario 3's mass email through `email.csv`. Detection relies on the logon, USB and file evidence alone, which is a deliberate scope trade-off.
- **Dirty data by design.** Some logons aren't recorded, and some USB connects have no disconnect.

# Part B — Synthetic testbed

## Provenance

| | |
|---|---|
| Generator | `src/ueba/generator.py`, written by the team (FR-2) |
| Nature | Fully synthetic. Names come from Faker and live only in the users directory, never in events |
| Licence | Our own code and data, so there are no redistribution limits. Faker is MIT-licensed |
| Reproducibility | Seeded. The same `GeneratorConfig` gives identical output, and every run writes its config next to the data |

## How to reproduce

```bash
.venv/bin/python -m ueba.generator --out data/processed/synthetic                 # defaults, seed 42
.venv/bin/python -m ueba.generator --seed 7 --users 200 --out data/processed/s7    # variations
.venv/bin/python -m ueba.generator --config sweep/mass_10x.json --out ...          # Intensity sweeps (RQ2)
```

Output: `{events,users,labels,injected_events}.parquet` plus `config.json`. The default run takes about 2 seconds.

## Design

**Period.** 42 days from 2026-08-20.

- **Baseline Window:** 2026-08-20 to 2026-09-16 (28 days). Normal behaviour only.
- **Detection Window:** 2026-09-17 to 2026-09-30 (14 days). Scenarios are injected here. It ends on a **quarter end**, so the Finance quarter-end rush (a Hard Negative) falls inside it.

**Organisation.** 120 users across 6 departments: Finance, HR, Engineering, Legal, Sales and IT. Each user has a role and an assigned PC (`PC-0001`…). Each department owns three file categories, each with a typical file type:

| Department | Categories (file type) |
|---|---|
| Finance | financial_report (pdf), invoice (pdf), budget (xlsx) |
| HR | hr_record (docx), payroll (xlsx), recruiting (docx) |
| Engineering | source_code (txt), design_doc (docx), test_data (zip) |
| Legal | contract (pdf), litigation (docx), compliance (pdf) |
| Sales | customer_list (xlsx), pricing (xlsx), proposal (docx) |
| IT | it_config (txt), access_log (txt), runbook (docx) |

**Normal behaviour, per user:**

- **Volume:** an activity rate of 10–30 file events per weekday. Weekends are rare (8% of weekends active, at 30% volume).
- **Hours:** a personal start time between 07:30 and 10:00, with events clustered around midday and clipped to business hours (07:00–19:00).
- **Files:** 85% of files come from the user's own department. Sensitivity of own-department files is public 25%, internal 50%, confidential 20%, restricted 5%. Files from other departments are almost never sensitive (2% confidential).
- **Actions:** view 60%, edit 25%, download 10%, print 4%, delete 1%.
- **USB and external sharing:** about 25% of users copy to USB occasionally (as in CERT), and half of Sales sometimes uploads externally. Without this, any USB copy would be a free giveaway for detectors.
- **Logons:** a logon and logoff pair around each burst of activity, with a new session after a 3-hour gap.

## Scenarios and Intensity

Anomalous Scenarios: 3 users each, 15 in total. Every Intensity value is a config parameter, so it can be swept for RQ2.

| Scenario | What is injected | Default Intensity |
|---|---|---|
| `mass_download` | One business day of downloads and USB copies of own-department files | 50× the user's normal daily transfers |
| `after_hours` | Activity between 22:00 and 04:00 on several nights, mostly confidential files | 4 nights × 25 events |
| `cross_department_sensitive` | Confidential or restricted files owned by other departments | 3 days × 12 accesses |
| `new_device_transfer` | Uploads, USB copies and downloads from an unmanaged device (`UNMANAGED-####`) | 2 days × 30 transfers |
| `slow_drip` | A few extra transfers on every Detection-Window weekday, with no single spike | +5 per weekday |

Hard Negatives (labelled `is_anomalous = False`):

| Hard Negative | Users | What it simulates |
|---|---|---|
| `benign_on_call` | 3 (from IT) | About 25% of activity at night **throughout the period**, so it's part of their own Baseline |
| `benign_quarter_end` | Every Finance user not otherwise labelled (19 by default) | 6–11 extra downloads each on the quarter-end day, a whole-department rush |
| `benign_new_hire` | 3 | Starts in the Detection Window with no Baseline history |

**Labels.** `window_start` and `window_end` span the injected events, or the hard-negative period. The IDs of every injected event are stored in `injected_events.parquet`, for event-level evaluation and error analysis.

**Avoiding self-grading.** The Data Lead owns these settings. The AI/RAG Lead tunes detectors without reading this section or the generator code, and then evaluates on fresh seeds.

## Known limitations

- **We designed it, so its patterns are only as realistic as our assumptions.** Results here show *relative* detector behaviour (RQ1–RQ3). CERT is the external check.
- **Behaviour is stationary.** There's no gradual drift in normal habits, holidays, role changes or team-wide projects other than the quarter-end rush.
- **Scenario patterns are clean.** Each anomalous user has exactly one scenario. Real cases mix behaviours.
- **Unrealistically dense.** 15 anomalous users in 120 (12.5%), similar to CERT's "dense needles". Real-world prevalence is far lower, so precision would drop.
